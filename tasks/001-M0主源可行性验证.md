## 目标

验证官方小程序"宝可梦卡牌会员"接口的可行性，完成 D1 决策：

- **路线 A**：主源 = 小程序接口（数据一手、结构化 JSON、字段最全）
- **路线 B**：主源 = tcg.mik.moe 镜像（公开网页、同源二手数据、零合规风险）

无论选哪条，两条 scraper 最终都要写（PRD 双源交叉校验），本任务只决定**谁主谁辅**。

## 步骤

### 1. 抓包环境（~1h，工具已备好）

**操作指南见 `tools/capture/README.md`**（mitmproxy 已安装于 `tools/capture/.venv`，流量录制到 `data/raw/capture/`）。

- [ ] 用户按指南完成 5 步：启动代理 → 装 CA 证书 → 设系统代理 → 操作小程序 → 停录制
- [ ] AI 用 `tools/capture/dump_flows.py` 分析 flows，筛出候选 API
- 备选方案（PC 微信抓不到时）：手机 + mitmproxy 代理，步骤等价

### 2. 接口定位（~2h）

在小程序中操作"卡查"功能，抓两类请求：

- [ ] **卡牌列表接口**：按系列浏览，记录 host、path、method、headers、query/body 参数、分页方式
- [ ] **卡牌详情接口**：点开一张卡（建议选机制复杂的，如火箭队的超梦ex 或太晶星晶卡），同上记录
- [ ] 检查响应是否为结构化 JSON、字段完整度（卡名/卡号/赛制标记/特性/招式/能量成本/弱点抵抗/进化关系）
- [ ] 观察是否含签名参数（sign/token/timestamp 组合）、设备指纹、登录态 Cookie

### 3. 可行性判定（~2h）

- [ ] **重放测试**：用 curl/httpx 脱离微信环境重放同一请求，能否拿到 200 + 完整数据
- [ ] **签名判定**：若带签名，改一个参数重放是否被拒绝；签名是否可静态还原（30 分钟还原不出即视为不可行）
- [ ] **礼貌探测**：以 ≤1 req/s 连续请求 10 次，观察是否触发频控/验证码/封禁提示

### 4a. 路线 A 可行时（~2h）

- [ ] 写一个最小 httpx 脚本跑通 1 个接口，样例响应落盘 `data/raw/miniprogram/sample_*.json`
- [ ] 接口文档写入 `docs/miniprogram-api.md`（endpoint、参数、鉴权、样例、字段映射到 PRD §7.2 的对照表）

### 4b. 路线 A 不可行时（~2h）

- [ ] 记录失败原因（签名/风控/登录态，具体到现象）
- [ ] 转而验证路线 B：检查 tcg.mik.moe 卡牌页结构，确认字段完整度（赛制标记、进化关系、能量成本是否可提取），写 1 个最小解析脚本验证

### 5. 输出 D1 决策（~1h）

- [ ] 按下方决策矩阵定 A/B，结论 + 理由写入 `STATUS.md` 决策日志

## D1 决策矩阵

| 情况 | 决策 |
|---|---|
| 重放成功、无签名或签名可还原、无频控 | **A**（小程序为主源，mik.moe 为校验源） |
| 有签名但 30 分钟内可还原 | **A**，但在风险登记册上调风控概率 |
| 签名无法还原 / 需登录态+设备指纹 / 触发风控 | **B**（mik.moe 为主源），M1 预算 +1~2 天 |
| 两条都走不通（极端情况） | 升级上报，重新评估数据源策略，不进 M1 |

## 验收标准

- [ ] D1 有明确结论（A 或 B）并写入 `STATUS.md` 决策日志，附理由
- [ ] 选 A：`docs/miniprogram-api.md` 接口文档 + 可重跑的验证脚本 + 样例响应入库
- [ ] 选 B：A 失败原因记录 + mik.moe 解析验证脚本，M1 预算调整同步到 `STATUS.md`
- [ ] 红线遵守：全程只读、≤1 req/s、不碰卡图、数据不外传（AGENTS.md）
